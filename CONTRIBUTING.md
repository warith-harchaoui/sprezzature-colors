# Contributing

## Setup

```bash
git clone https://github.com/warith-harchaoui/sprezzature-colors
cd sprezzature-colors
pip install -e ".[dev]"
```

## Tests

```bash
pytest
```

## Lint

`ruff` is the Python linter and formatter this project uses: it reads
the source without running it and flags style issues (unused imports,
wrong quote style, and the like) in one fast pass.

```bash
ruff check .
```

The pre-push hook also runs mypy, once on the package and once on the scripts:

```bash
mypy sprezzature_colors
mypy scripts
```

## Adding a script

1. Put shared color math in `scripts/_colors.py`, not in the new
   script. Every existing script (`audit_contrast.py`,
   `simulate_cvd.py`, `accessibility_levels.py`,
   `palette_to_tailwind.py`) imports its color primitives from there;
   a new script should do the same rather than reimplementing sRGB or
   OKLCH (OK Lightness Chroma Hue, a colour model in which equal steps
   look equally different to the eye) conversion.
2. Build the script's command with click, through
   `_click.sprezzature_command(name=..., help=...)`, and keep
   `main(argv: list[str] | None = None) -> int` returning
   `_click.run_command(cmd, argv)`, so `-h`, `-V/--version`, the help
   layout and the exit codes (2 on a usage error) stay the same across
   scripts. argparse is not used anywhere in this package, and
   `tests/test_every_command_is_click.py` fails if it comes back. The front door
   (`sprezzature-colors`, in `sprezzature_colors/cli.py`) is click and
   hands the arguments through unchanged.
3. Register the tool in `TOOLS` in `sprezzature_colors/_tools.py`. That
   table is what makes it a sub-command of `sprezzature-colors` and a
   line of `sprezzature-colors tools`.
4. Add its console script to `[project.scripts]` in `pyproject.toml`,
   as `sprezzature-colors-<name>`. `scripts/` is already mapped to the
   `sprezzature_colors_scripts` package, so nothing else in
   `pyproject.toml` changes.
5. Add a test in `tests/test_colors.py`.
6. Document the script in `EXAMPLES.md` and in the relevant `README.md`
   / `LISEZMOI.md` quick-start section. If the script is substantial
   enough to need design rationale (not just usage), add a matching
   `references/<script-name>.md`. If it is reachable by an agent, add it
   to both tables of `TRIGGERS.md`, and to the decision tree and the
   scripts table of the skill, `sprezzature_colors/skill/SKILL.md`.

## The skill

The skill an agent reads ships inside the package, in
`sprezzature_colors/skill/`: `SKILL.md`, and in `references/` the
reference documents, `palette.csv` and `triggers.md`. `pyproject.toml`
carries it into the wheel (`skill/**/*` under package-data), and
`tests/test_the_skill_ships_with_the_package.py` checks that it does.

- `sprezzature-colors-skill` (or `sprezzature-colors skill`) reports
  whether the copy under `~/.claude/skills` is in step; `--install`
  refreshes it, `--agent opencode` targets `~/.opencode/skills`.
- The `description:` field of the front matter and
  `references/triggers.md` are generated by the hub's
  `scripts/build_triggers.py`; do not edit them by hand.
- `sprezzature_colors/_skill.py` and its test are shared verbatim by the
  ten bricks and kept in step by the hub's `scripts/sync_helpers.py`;
  change them in the hub, not here.
- The repository's own `references/*.md` and the skill's
  `sprezzature_colors/skill/references/*.md` are two copies of the same
  documents, the first written for a source checkout
  (`python scripts/...`), the second for an installed package
  (`sprezzature-colors-...`). Change both.

## Code standards

See `CODING.md`. NumPy docstrings, full typing, ~25-30% comment
density.

## Prose standards

See `references/WRITING.md` (EN) and `references/ECRITURE.md` (FR).
